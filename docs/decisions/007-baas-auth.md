# 007: BaaS・ログイン方式

- Status: DECIDED（メール送信サービスのみ PROPOSED）
- Date: 2026-09-28
- Area: Technical
- Related: [baas-comparison](../research/2026-09-28-baas-comparison.md), [backend-auth-hosting](../research/2026-09-28-backend-auth-hosting.md), [005](005-platform.md), [006](006-hosting.md), [mvp](../product/mvp.md)

## Context

- Web のみ（PWA）で提供する（[005](005-platform.md)）。
- 開発者は Web フロントエンドのエキスパート。バックエンドは経験が少なく、BaaS（Supabase など）を使いたい。
- 予算の目安は年 1 万円（質が落ちるなら増額可）。1 人保守。
- MVP の要件（[mvp](../product/mvp.md)）:
  - 誰でも登録できる。招待リンクで招待者を自動フォロー。
  - フォロー、タイムライン、いいね、コメント、延べ再生回数、ログインなし閲覧。
- 招待リンクは LINE で送られることが多く、LINE のアプリ内ブラウザで開かれうる。そこでは Google ログインが失敗する。
- パスワードを自前で保存しない方式を優先する（R8）。

## Options considered

### バックエンド

詳細: [baas-comparison](../research/2026-09-28-baas-comparison.md)

| Option | メリット | デメリット | 相性 | 後から変更できるか |
|---|---|---|---|---|
| **Supabase** | リレーショナル DB（フォロー・タイムラインを素直に作れる）。認証・行ごとのアクセス制御（RLS）が一体で、サーバー側のコードが最小。無料で商用可。開発者の希望 | 無料プランは 1 週間無操作で停止・バックアップなし。Pro は月 25 USD | 高い | DB は標準の Postgres で移しやすい。認証は Supabase 依存 |
| Firebase | 無料枠が広く、停止しない | NoSQL でタイムラインの設計が複雑。メールの 6 桁コードが標準か要確認 | 中 | 作り直しに近い |
| Convex | TypeScript で書ける。リアルタイム更新が得意 | 独自 DB。認証は別途。無料プランの条件に未確認点あり | 中 | 作り直しに近い |
| Neon ＋ 自前の認証（Better Auth 等） | 標準の Postgres ＋オープンソースで最も移しやすい | 認証とアクセス制御を自分で書く量が増える（バックエンド経験が少ない） | 中 | 最も容易 |
| Appwrite | 複数の DB を選べる | 情報が少なく、無料プランの条件に未確認点あり | 低い | 中 |

### ログイン方式

| Option | メリット | デメリット |
|---|---|---|
| **メールで届く 6 桁のコード** | どのブラウザでも使える（LINE のアプリ内ブラウザでも）。パスワード不要 | メール送信サービスと独自ドメインが必要。毎回メールを見る手間 |
| **Google ログイン** | ワンタップで楽 | LINE のアプリ内ブラウザでは失敗する（外部ブラウザで開かせれば問題なし） |
| Apple ログイン | iPhone の人に楽 | Web での利用条件が未確認（Apple Developer Program が必要な可能性） |
| LINE ログイン | 友人が全員使っている。LINE 内で完結 | Supabase ではそのままでは動かないという報告あり。実装が重い |
| メール＋パスワード | 一般的 | パスワード管理の手間とリスク（R8） |

## Decision

開発者の決定（2026-09-28）。

- バックエンド: **Supabase（無料プラン）**。
  - 停止対策: 開発中に停止したら、管理画面から再開する。
  - バックアップ: GitHub Actions で DB を定期的に書き出す。
- ログイン: **メールの 6 桁コード ＋ Google ログイン**。
  - 招待リンクには `openExternalBrowser=1` を付け、外部ブラウザで開かせる。
  - [PROPOSED] メール送信は Resend の無料枠を使う。Supabase 標準のメール送信は 1 時間 2 通まで・チームメンバー宛てのみで、本番には使えないため（[Supabase Docs](https://supabase.com/docs/guides/auth/auth-smtp)）。
- 独自ドメインを取得する（メールの送信元と PWA に必要）。

## Why

- 開発者の希望（BaaS）と、SNS のデータ構造（フォロー・タイムライン）に最も合う。
- バックエンドの経験が少なくても、DB・認証・アクセス制御を 1 か所で扱え、自分で書くコードが最も少ない。
- DB は標準の Postgres なので、将来 Neon などへ移る道が残る（取り返しのつかない選択を避ける）。
- 2 つのログイン方式で、LINE のアプリ内ブラウザ問題と、手軽さの両方に対応できる。
- 費用はドメイン代（年 数千円）のみで、予算の目安に収まる。

## Tradeoffs / Consequences

- Supabase 無料プランの制約（停止・バックアップなし）を運用で補う。
- 認証（ユーザー情報）は Supabase に依存する。移る場合は、ユーザー情報の移行が必要。
- 固定費: ドメイン代のみ（年 数千円）。

## Revisit when

- 利用者が増え、無料枠（DB 500MB、転送 5GB、メール 1 日 100 通）に近づいたとき
- データを失うリスクが許容できなくなったとき（→ Supabase Pro の日次バックアップ）
