## 1. Strategy in one line [DECIDED]

> 知り合い同士が「意図して 1 曲を勧める」ことに絞り、サービスの違いを気にせず、すぐ試聴して反応できる場をつくる。

## 2. Where to play / How to win [DECIDED]

| | 内容 |
|---|---|
| 誰のために | 開発者（Spotify）と友人約 20 人（Apple Music が多い）。次に、友人の友人 |
| どんな場面で | 「この曲いい、あの人に聴いてほしい」と思ったとき |
| 何で勝つか | ①すぐ試聴できる（サービスの違いを問わない） ②登録・参加の手間が小さい ③日本の楽曲に強い照合 |
| 戦わない場所 | 今聴いている曲の自動共有（Airbuds）、DM（Spotify Messages）、知らない人との出会い・発見 |

## 3. Core Loop（仮説）[HYPOTHESIS]

利用が続く仕組みの仮説。MVP（Phase 8）はこのループが回るかを確かめる最小単位にする。

```
[入口] 開発者が友人に「こういう SNS を作ったから使って」と声をかけ、登録してもらう
① 1 曲＋一言を投稿
  → ② 友人が新しい投稿に気づく（主に暇なときにアプリを開いて見る。通知は各自の設定次第）
  → ③ その場で試聴する（H4 / H1）
  → ④ いいね・リアクション・コメントする
  → ⑤ 投稿者に反応と再生回数が届く（H9）
  → ①に戻る（投稿者はまた投稿したくなる / 見た友人も投稿したくなる）
```

- 投稿のリンクを LINE / X で共有する使い方は想定しない（開発者の回答）。
- ログインしていなくても投稿を見られるのはあってよい（X のように）。ただし、広げる手段としては位置づけない。
- 開発者の想定する使い方（2026-09-28 回答）:
  - アプリを開くのは暇なとき（X を見る感覚）。
  - 基本は、気が向いたときに見るだけでよい。
  - 投稿があったときの通知は、各自が設定で選べればよい。
- そのため、タイムラインの過疎（R1）への対策は「暇なときに開いて、見るものがある」ことにかかる。新しい投稿が少ない日にも見る価値があるか（→ Phase 7）。

## 4. Product Principles [DECIDED]

判断に迷ったときの優先順位。上ほど優先する。

1. **聴くまでの手間を最小にする。** 試聴は最優先の体験。
2. **サービスの違いを意識させない。** 投稿者も閲覧者も、自分のサービスのまま使える。
3. **参加の手間を小さくする。** 声をかけられた友人が、すぐに登録して使い始められる。
4. **投稿は軽く。** 1 曲＋一言。気が向いたときだけでよい。
5. **聴く側に負担をかけない。** 誰が聴いたかは見せない。毎日開くことを求めない。
6. **小さく、安く、保守しやすく。** DM・アップロードなし。外部 API への依存は曲の検索・情報・試聴に限る。

## 5. Do / Don't [DECIDED]

| やる | やらない（当面） |
|---|---|
| 1 曲の投稿＋一言 | アルバム・プレイリスト単位の共有 |
| サービスをまたいだ試聴と、各自のサービスへのリンク | Spotify / Apple Music のユーザー連携（ログイン・再生履歴の取得） |
| いいね・その他のリアクション・コメント | DM（決定済み） |
| 投稿者だけが見る再生回数 | 誰が聴いたかの表示 |
| 各自が見たい人をフォローする（片方向） | おすすめ・全体タイムライン・知らない人との出会い |
| 新しい投稿の通知（オン / オフは各自の設定） | グループ機能（下記メモ） |
| 最低限の通報・削除・ブロック、利用規約・プライバシーポリシー | 画像・音声・動画のアップロード（決定済み）、収益化 |

### メモ: フォローとグループ

- 開発者の回答: フォローでよい。グループは「いちいちフォローしなくてよい」点で面白いが、X などがそうしていないようにデメリットもありそう。
- AI の補足（意見）:
  - グループのデメリットは主に 2 つ。「誰を入れるか」の境界の管理と、複数のグループに入ったときの重複や見え方の複雑さ。
  - 一方、フォロー制の弱点は、新しく登録した人が友人を 1 人ずつフォローしないとタイムラインが空になること（R1）。
  - この弱点は、グループを作らなくても、登録時の工夫で和らげられる可能性がある（例: 誘ってくれた人や、その人がフォローしている人をまとめてフォローできる。Phase 7 で比較）。

## 6. Target Devices [DECIDED]

- iPhone と Android の両方で使えること。
  - 理由: 開発者は Android、友人は iPhone が多く Android もいる（2026-09-28 回答）。
- どう実現するか（Web / ネイティブ等）は Phase 9 で決める。
  - 費用（Apple Developer Program）と、通知の実現方法が主な比較軸になる。

## 7. Stages [DECIDED]

| Stage | 対象 | 目標 | 次に進む条件 |

## 8. Metrics（案）[PROPOSED]

- 成功基準（決定済み）: 友人 10 人が公開 3 か月後も週 1 回以上、投稿または試聴している
- ループを見るための補助指標:
  - 週あたりの投稿数
  - 投稿あたりの試聴数
  - 声をかけた友人のうち、登録した人の割合
