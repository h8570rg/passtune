# 開発者ヒアリング 第1回

- Date: 2026-09-28
- Phase: 2（[003](../decisions/003-user-research-approach.md) により、開発者本人へのヒアリングで代える）
- Question: 音楽を共有する／される場面で何が起きていて、どんな体験が欲しいか
- Related: [vision.md](../product/vision.md), [音楽 API 調査](2026-09-28-music-api-feasibility.md)

## TL;DR

- **聴くかどうかは「すぐ試聴できるか」で決まる。** 簡単に試聴できない曲は、勧められても聴く気にならない。自分が勧めるときも試聴できるようにしたい。
- **反応が欲しい。** いいね、簡単なコメント、「聴いた」ことが分かる表示。
- **共有の単位は 1 曲。** 投稿として見たいのは「曲＋一言コメント」。

## Findings

### Facts（開発者の発言）

- 友人から曲を勧められても、簡単にプレビューできないと聴く気にならない。
- 自分がおすすめするときも、簡単にプレビューできるようにしたい。
- リアクションが欲しい。いいね機能と簡単なコメント機能が欲しい。
- 相手が聴いたことが分かるのはよい。
- 共有するのは 1 曲。
- 投稿は、曲と一言コメントが見たい。

### Inferences（AI の推測）

- 試聴できるかどうかが、H4 の中心であり、このプロダクトの体験の核になる。H1（サブスクの違い）の困りごとも、「自分のサービスで開けない → 試聴できない → 聴かない」という形で試聴の問題に含まれる可能性がある。
- 共有する側の動機は、反応（いいね・コメント・聴いた表示）によって支えられる。X では反応が得にくいこと（H7）とつながる。
- 開発者は Spotify ユーザーで、Spotify の曲を勧めることが多いと考えられる。一方、[API 調査](2026-09-28-music-api-feasibility.md) では Spotify API から試聴音源は取れない。そのため「Spotify の曲を、どう試聴させるか」が最大の技術的な論点になる（決定は Phase 7 / 9）。

## Implications

- 問題仮説 H4 は、開発者本人については強く当てはまる。H9（反応が共有の動機になる）を追加する。
- プロダクト原則の候補:「聴くまでの手間を最小にする」「投稿は 1 曲＋一言で軽く」。
- 解決策のアイデアに、いいね、コメント、「聴いた」表示を追加する（採否は Phase 7〜8）。

## Open / Next

- 「聴いた」ことが相手に分かるのは、自分が聴く側のときも抵抗がないか（プライバシーの感覚）。
- どのくらいの頻度で投稿しそうか。
- X に投稿したときの反応の実際（H7 の具体例）。

## 追加回答（同日）

### Facts（開発者の発言）

- Spotify の曲の試聴は、同じ曲を Apple 側で探して、その試聴音源を使うのがよいと思う（解決策への意向）。
- 「聴いた」表示は、自分の投稿が何回再生されたかを自分だけが見られればよい。誰が聴いたかは表示しなくてよい。
- リアクションは、いいね以外にもあってよい。
- 投稿は気が向いたときだけ。

### Inferences（AI の推測）

- 「聴いた」の情報は、投稿者だけが見る再生回数に限定される。そのため、聴く側の心理的負担（見られている感）を避ける形になる。
- 投稿は不定期なので、友人 20 人規模だとタイムラインが空きやすい。空のタイムラインは、成功基準（週 1 回以上使う）にとってリスクになる（→ Phase 5 / 7 で扱う）。
- Apple 側の試聴を使う案には、次の確認事項が伴う（→ Phase 7 / 9）。
  - 曲の照合の精度
  - Apple Music にない曲の扱い
  - iTunes Search API の利用条件（Apple Music へのリンクの併置など）
